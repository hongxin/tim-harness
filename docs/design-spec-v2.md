# 对比分析：为什么 Anatomy 好而我们的差

## 本质差异（不是视觉细节，是设计思维）

### Anatomy 的设计原则
1. **讲一个故事**：从上到下 = 从"用户想要什么"到"结果是什么"
2. **每个元素有明确的语义位置**：漏斗在顶（输入）、齿轮在中（处理）、滑道在底（输出）
3. **大小 = 重要性**：思考齿轮最大（核心），工具适中（执行者），仪表最小（监控）
4. **连接 = 数据流**：你能trace一个"数据包"从输入到输出的完整路径
5. **约束可见**：上下文是物理容器（会满的）、token是燃料表（会耗尽的）

### 我们的问题
1. **没有故事**：只是一堆彩色方块在卡片里
2. **位置随机**：工具在treemap里的位置没有逻辑
3. **大小无意义**：面积编码了复杂度，但这不是用户关心的
4. **连接无方向**：没有"数据从哪来到哪去"的感觉
5. **约束不可见**：没有上下文容量的视觉暗示

## 正确的设计

```
对于一段 3 回合对话，应该讲这个故事：

  回合1：分析          回合2：实现          回合3：验证
  ┌──────────┐       ┌──────────┐       ┌──────────┐
  │ 👤 分析项目 │──────▶│ 👤 实现功能 │──────▶│ 👤 验证    │
  │    ↓      │       │    ↓      │       │    ↓      │
  │ 🧠 思考    │       │ 🧠 思考    │       │ 🧠 思考    │
  │    ↓      │       │    ↓      │       │    ↓      │
  │ 🔍 ls     │       │ ✍️ write  │       │ ⚡ run    │
  │    ↓      │       │    ↓      │       │    ↓      │
  │ 📖 read   │       │ ⚡ run    │       │ ✅ 通过    │
  │    ↓      │       │    ↓      │       │          │
  │ 🎯 grep   │       │ ✅ 完成   │       │          │
  │    ↓      │       │          │       │          │
  │ ✅ 完成   │       │          │       │          │
  └──────────┘       └──────────┘       └──────────┘

  底部约束条（贯穿全部回合）：
  ┌─────────────────────────────────────────────────┐
  │ 上下文容器: ████████░░░░░░░░ 45%                 │
  │ Token燃料:  ▓▓▓▓▓▓░░░░░░░░░ 2,847               │
  └─────────────────────────────────────────────────┘
```

## 关键设计决策

1. **每回合 = 一个垂直管道**（从上到下 = 时间顺序）
2. **回合从左到右排列**（时间线推进）
3. **管道内部：用户(顶) → 思考(中) → 工具序列(下) → 结果(底)**
4. **连接线：回合间是水平流（A→B→C），回合内是垂直流（top→bottom）**
5. **底部约束条：始终可见的上下文/token 状态**
